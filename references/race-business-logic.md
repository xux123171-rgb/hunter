# 业务逻辑 + 并发(race)洞 —— 我们的参考

**定位**：SOP 阶段 4.2「业务逻辑」行的展开。WAF 全盲（见 waf-bypass.md 第 3 节），是强防护目标的最高性价比线。

## A. 业务逻辑洞（状态机 / 金额 / 越权 / 跳步）
探测法（全合规，改动 ≤ 最小可证）：
- **金额/数量篡改**：下单改 `price=1`、`qty` 负数、`discount=99` → 服务端是否照收。实锤：能真下一单（用我们自己的号，最小金额/可退）。
- **跳步**：直接请求"第 3 步"端点而不走第 1、2 步 → 是否放行。实锤：直接到结果页/拿到资源。
- **越权角色**：普通号打 `/admin/*`、改 cookie 里 `role` 字段 → 真执行管理操作才算。
- **状态竞态**：优惠券/库存/余额类，见 B。

判死：每处都有**服务端兜底校验**（重算价格/回查库存/权限二次校验）→ 逻辑线判死。

## B. 并发 / race condition（TOCTOU）
适用：余额、优惠券、库存、限次兑换、关注数、投票、点赞——"检查"和"使用"之间有时间窗。
```
正常流：  check(余额≥100) → deduct(100)
攻击：    发 N 个并发请求，全部在 check 前到达、都读到余额=100、全部 deduct
```
打法（克制，合规）：
1. 手动确认端点有效、单发 1 次成功、记录基线（余额/库存）。
2. **并发 2~5 个**同请求（`for i in 1..5: curl ... &` + `wait`）——**不做高并发轰炸**（那是 DoS 线，越红线）。
3. 看结果：多个"成功" / 余额变负 / 库存超扣 = race 成立。实锤：余额/库存真变。
4. 判死：服务端有 `SELECT ... FOR UPDATE`/原子 `INCR`/去重键 → 并发 N 个只有 1 个成功、其余被拒 → 判死。
> 我们**不用 Turbo Intruder**（付费 Burp 扩展、且单包攻击偏攻击向）。用 shell 并发 2~5 个足够合规证明 race，且 payload 克制。

## 与双账号的协作
越权/IDOR/横向逻辑洞要 **2 个登录态账号** → 走 `tools/mailacct.py`（邮箱）+ 手机号（用户侧）。拿 2 号后：A 号资源 ID 给 B 号打 = IDOR；A 改 B 的对象 = 越权写。
